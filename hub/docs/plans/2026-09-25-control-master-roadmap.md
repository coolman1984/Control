## الجزء الأول — للمالك: الخلاصة بالمصري

### 🎯 الهدف في جملة
البرنامج النهارده **إيدين وعينين** للذكاء الاصطناعي على جهازك. الخطة دي بتديله **مخ ومنبّه وذاكرة وحارس أمن** — عشان يشتغل لوحده بمواعيد وأحداث، ويكمّل لو وقع، ويبلّغك، ويستأذنك في الخطر بس.

### 📍 إحنا فين دلوقتي
- ✅ عندنا: تحكم في برامج الويندوز، تشغيل تقارير النظام الصناعي، صيانة الجهاز، تحليل ملفات الإكسل، وتصنيف أمان وسجل ورجوع.
- ❌ ناقصنا: **تشغيل تلقائي** (كل حاجة لازم حد يطلبها)، **سلاسل خطوات محفوظة** بتكمّل بعد الأعطال، **لوحة متابعة**، **خزنة كلمات سر عامة**، **تنبيهات**، ومحرك مواقع عام مش للنظام الصناعي بس.

### 🧱 الخطة في ٨ مراحل (بالترتيب)

| # | المرحلة | بتديك إيه | الأولوية |
|---|---|---|---|

| ٤ | 🔐 **الخزنة والحارس** | كلمات السر متشفرة وعمر الذكاء الاصطناعي ما يشوفها، زرار طوارئ يوقف كل حاجة، وحماية من المواقع اللي بتحاول تضحك عليه | 🔴 |
| ٥ | 🌐 **محرك المواقع العام** | خبرة النظام الصناعي (الدخول، الانتظار الذكي، التأكد قبل الحفظ) تتعمم على أي موقع | 🟠 |

### 💡 أهم ٥ أفكار في الخطة
1. **الذكاء الاصطناعي بيصمم، والمحرك بينفذ** 🧩 — المهمة المتكررة تتحفظ خطوات ثابتة تشتغل من غير ذكاء اصطناعي (أسرع، أرخص، ومضمونة)، وهو يتدخل بس لما حاجة تتغير.
2. **كل خطوة ليها نقطة حفظ** 💾 — زي ألعاب الفيديو: لو النور قطع، تكمّل من آخر نقطة مش من الأول، ومفيش حاجة تتعمل مرتين.
3. **الإذن بيتاخد مرة للسلسلة كلها** ✍️ — بتوافق على السلسلة وهي مقفولة، ولو حد غيّر فيها حرف الإذن يتلغي تلقائي.
4. **اللي جاي من برّه مشبوه** 🛡️ — أي كلام جاي من موقع أو إيميل أو ملف ميقدرش يأمر بحاجة خطيرة، حتى لو الذكاء الاصطناعي اقتنع.
5. **الشغل الحقيقي محتاج شاشة مفتوحة** 🖥️ — البرامج اللي بتتحكم في الشاشة مينفعش تشتغل والجهاز مقفول؛ فالخطة فيها حل واضح: جهاز مخصص أو جلسة مفتوحة محمية.

### ⚖️ قرارات محتاجة منك
- هل التشغيل التلقائي يكون **على جهازك الشخصي** ولا **جهاز مخصص** للشغل ده؟ (المخصص أأمن وأقوى)
- التنبيهات توصلك فين؟ **إشعار على الويندوز** بس، ولا كمان **إيميل/موبايل**؟
- الموافقة على الخطر: من **الشاشة بس** (زي دلوقتي) ولا نسمح **من الموبايل** كمان؟

### 🚫 اللي مش هنعمله
برنامج لأكتر من شخص، أو خدمة سحابية، أو رسام سلاسل بالماوس في الأول — دول بيكلّفوا كتير وبيبطّأوا الأساس.

## Part 2 — Build plan (for the engineers and agents who will build it)

### 2.0 Research basis (what "real" automation platforms have that we don't)

| Capability in mature platforms | Where it lives there | Control today |
|---|---|---|
| Orchestrator: queues, schedules, run history, RBAC, audit of every robot action | UiPath Orchestrator | journal only, no runs/queues |
| Triggers: time, file arrival (2nd most used), e-mail, app/desktop event, webhook | UiPath, Zoho RPA, Fortra Automate, Robomotion | none |
| Durable execution: checkpoint each step, resume after crash, no double side-effects | Temporal, DBOS (embedded, SQLite-backed), Restate, Hatchet | none |
| Credential vault, secrets never shown to the model | Copilot Studio computer use (internal store / Key Vault) | G-MES only (DPAPI) |
| Layered targeting: UI tree → selectors with anchors → computer vision for Citrix/RDP | UiPath AI Computer Vision, OmniParser V2 | UIA + OCR + optional OmniParser (wad) |
| Observability: success rate, duration, step screenshots, replay, masked logs | RPA monitoring products, Splunk RPA | wad `report` (off by default) |
| Task mining: discover repetitive work from desktop activity | UiPath Task Mining, Power Automate Process Advisor, PM4Py | wad `record` only |
| MCP safety: least privilege, per-operation time-bound consent, tool allowlists, full audit, prompt-injection & tool-poisoning defence | MCP security best practices, CSA agentic MCP guide, NSA MCP CSI (Jun 2026) | tiers + approval box + journal |

Design stance taken from this: **deterministic robot layer + agent layer on top** (the 2026 pattern of UiPath Maestro / Copilot Studio): the agent authors and repairs flows; flows run without a model.

### 2.1 Target architecture

```
                 ┌──────────── Claude / any MCP client ────────────┐
                 │   control mcp  (actions + flow.* + run.*)       │
                 └───────────────────────┬─────────────────────────┘
 triggers ──► ┌──────────────────────────▼──────────────────────────┐ ◄── tray app / dashboard
 (time, file, │  control agent (per-user, interactive session)      │     (localhost only)
  mail, win,  │  scheduler · trigger bus · flow engine · run store  │
  event log,  │  approvals · vault · policy · notifier              │
  webhook)    └───┬──────────┬──────────┬──────────┬─────────┬──────┘
                  │          │          │          │         │
                 win.*     web.*      gmes.*     sys.*     data.*  (+ os.* elevated broker)
```

- **`control agent`**: long-running per-user process started by a Task Scheduler "at logon" task (not a Windows service: services live in Session 0 and cannot see or drive the desktop). A small watchdog task restarts it.
- **Run store**: one SQLite DB `%LOCALAPPDATA%\Control\control.db` (WAL) — runs, steps, checkpoints, queues, trigger state, approvals. Journal JSONL stays as the append-only audit trail.
- **Everything still goes through `runner.execute`** — flows get no side door around tiers, journal or approval.

### 2.2 Piece 2 — Flow engine (durable execution) 🔴 ✅ first version built (2026-09-25)

Owner decisions locked in: this runs on the owner's own PC (Windows-only), and risky-step
approval stays on-screen only (no phone approval channel) — piece 4's kill switch/vault follow
that same "screen only" line.

Built as `control/flow/` (`model.py`, `expr.py`, `engine.py`) + `control/store.py` (the run/
approval/lock store) + `control/areas/flow.py` (`flow.*`/`run.*` actions), with
`hub/tests/test_flow_*.py` + `test_store.py` + `test_area_flow.py`. One deliberate change from
this plan as first written: flows are **TOML, not YAML** — piece 1's Global Constraints keep
`control/` stdlib-only, and Python ships `tomllib` but no YAML reader; TOML's array-of-tables
syntax nests `if`/`for_each`/`parallel` cleanly (verified before committing to it). See
"Flows" in `docs/PLAYBOOK.md` for the owner-facing how-to and a worked example.

Delivered: `if`/`for_each`/`parallel`/`wait_for`/`ask_human`/`call_flow`/`set`/`assert` step
types; per-step retry with backoff and a retryable-code list; `for_each` keeps going after one
item fails and reports which; a flow-version approval (sha256 of the file) that once granted lets
every risky step inside run unattended until the file changes; crash/resume semantics (a step
found `started` with no `done`/`failed` after it means the process died — resumed automatically
only if `idempotent = true`, otherwise the run stops at `needs_attention` for `run.retry_step`);
a per-flow single-flight lock (`concurrency = "single"`, the default) so two runs of the same flow
never fight each other; a process-wide lock serialising real mouse/keyboard actions across
concurrently-running flows; `wait_for` refuses to poll a non-read action so it can't spam the
approval box or repeat a side effect; `flow.dry_run` previews without side effects, resolving
what it can and noting where it can't.

Known, documented v1 limits (fast-follows once a real flow needs them): `ask_human`/`wait_for`
may only be top-level steps (rejected by `flow.validate` if nested) — a pause has to be somewhere
resumable; `if`/`for_each` run their nested steps as one all-or-nothing unit, so a crash inside one
goes to `needs_attention` rather than resuming mid-loop; `call_flow` cannot call a sub-flow that
pauses (`CALL_FLOW_WAITING`); `for_each` items are a flat list processed sequentially (no queue
table yet — piece 3's per-item retry API is a natural extension once triggers need it).
- **Expressions**: small safe expression language (no `eval`): `{{steps.report.manifest.files[0]}}`, `{{secret:gmes}}`, `{{input.date}}`.
- **Durability** (DBOS-style, embedded, no server): each step's input/output recorded before continuing; on restart, completed steps are replayed from the store, not re-executed. Each step declares `idempotent` or an `idempotency_key`; non-idempotent step interrupted mid-flight → run goes to `needs_attention`, never auto-retried.
- **Retries**: per-step policy (attempts, backoff, retry-on codes list); `GMES_BUSY`/`TIMEOUT`/`APP_HUNG` retryable by default, `APPROVAL_DENIED` never.
- **Compensation**: optional `undo:` per step; failed run can roll back completed steps using journal undo pointers (saga).
- **Queues / work items**: `queue.add`, `for_each_item` with per-item status, so 500 rows = 500 tracked items, one failing does not kill the batch (UiPath queue model).
- **Global exception handlers**: flow-level `on_popup` rules ("dialog titled X → press Enter"), `on_error` flow.
- **Versioning**: flows in `%LOCALAPPDATA%\Control\flows\` under git; running runs pin the version they started with.
- **Actions**: `flow.list/describe/validate/run/dry_run`, `run.list/get/cancel/resume/retry_step`.
- **Pre-approval**: owner approves a flow version once; approval stored as hash of the flow file + its risky steps + argument bounds. Any edit invalidates it. Approvals can expire.
- **Done means**: a "G-MES report → xl2ai analyse → Outlook draft" flow survives a kill -9 mid-run and completes on restart with no duplicate report; unit tests cover replay, retry, compensation, invalidated approval.

### 2.3 Piece 3 — Triggers & scheduler 🔴

| Trigger | Mechanism |
|---|---|
| time / cron, calendar exclusions (holidays, shift days) | in-agent scheduler, missed-run policy (`skip`/`run_once`/`catch_up`) |
| file arrives / changes | `ReadDirectoryChangesW` + "file stable for N s" + glob + dedupe by hash |
| e-mail arrives | Outlook COM `NewMailEx` (fallback: poll) with sender/subject/attachment filters |
| window / app appears, process start/stop | wad UIA events + WMI process events |
| Windows event log | `EvtSubscribe` XPath query (e.g. disk errors → `sys.doctor` flow) |
| system state | WinSight monitor thresholds (disk < X GB, RAM, temperature) |
| data changed | xl2ai `changes` facts after refresh |
| hotkey | global hotkey → run flow |
| local webhook | `127.0.0.1` only, token-protected, off by default |
| manual | CLI / tray / dashboard / Claude |

- Debounce, concurrency limit per flow (`single`/`queue`/`parallel:N`), and a global "one UI flow at a time" lock (two flows cannot both drive the mouse).
- **Done means**: dropping an Excel file into a watched folder starts exactly one run; reboot-while-scheduled catches up per policy.

### 2.4 Piece 4 — Vault, policy and the guard 🔴

- **Vault**: Windows Credential Manager / DPAPI (current user), generalising `gmes_credentials.py`. Actions reference `{{secret:name}}`; the runner resolves it **after** the approval box and **inside** the adapter — the value never enters model context, journal, screenshots (mask the focused password field) or error text.
- **Untrusted-content taint**: output of `web.text`, `data.read`, e-mail bodies, OCR is marked untrusted. A risky action whose arguments came from untrusted content in the same session gets a stronger approval box that shows the source ("this command came from a web page"). Mitigates prompt injection, per MCP security guidance.
- **Policy file** (`policy.toml`): per-flow allowlists (actions, apps, folders, domains), argument bounds, rate limits (e.g. max 20 file deletes/run), business hours.
- **Kill switch**: global hotkey + tray button → cancel all runs, release inputs, journal it. Also "pause while the owner is using the mouse" option for attended mode.
- **Dry-run / simulation mode**: every safe/risky action returns what it *would* do.
- **Close the known gap** from piece 1: UI-chain bypass — a flow/session-level budget of UI actions touching shells, terminals, regedit, Control's own files → approval.
- **Tool-description integrity**: generated tool list is hashed at build; the MCP server refuses to serve descriptions changed at runtime (tool-poisoning defence).
- **Done means**: red-team test suite — injected web page asks the agent to run `win.shell`; secret never appears in any log; kill switch stops a running flow within 1 s.

### 2.5 Piece 5 — General web engine 🟠 (was "piece 2" in the hub spec)

- Lift G-MES's site-independent half into `web.*`: proxy bypass, trusted mouse events, stale-socket reconnect, polling waits, verify-before-save, screen memory, DPAPI login, download manager (wait for file complete, rename, hash).
- **Site plug-ins**: `sites/<name>.toml|py` = login recipe, known screens, selectors, verifiers. G-MES becomes plug-in #1 (the G-MES repo stays untouched; the adapter wraps it until parity).
- Session health: detect logged-out / SSO pages and re-login through the vault.
- Network capture (CDP) to read data from API responses instead of the screen where allowed — faster and more reliable than scraping.
- MCP concurrency: worker thread + per-area locks (deferred from piece 1) so a 20-minute report does not block other calls.

### 2.6 Piece 6 — Full Windows control 🟠 (was "piece 3")

- New `os.*` area: services, scheduled tasks, registry (with old-value undo), environment, printers, network adapters/proxy, clipboard, files (copy/move/rename with undo; delete → Recycle Bin), archives, shortcuts, installed apps via winget.
- **Elevation broker**: a separate elevated helper started once via UAC, speaking a narrow named-pipe protocol with an allowlist of verbs; the main process stays non-elevated. Solves "admin apps are invisible" and admin fixes without running everything as admin.
- wad old-value undo pointers; resumable multi-step undo.
- Office depth: Excel via COM with read-back already; add Excel refresh-all + wait, pivot refresh, PDF export, mail merge; Outlook rules/folders; Teams/Outlook meeting read.
- Optional **ERP plug-in**: SAP GUI Scripting through COM (pywin32) if the company's SAP allows scripting — deterministic popup handling and post-run validation.

### 2.7 Piece 7 — Stronger eyes, self-healing 🟡

- **Object repository**: named targets per app (`excel.ribbon.save`) with primary selector + fallbacks (automation id → name+role → anchor-relative → OCR text → vision). Flows reference names, not raw selectors.
- **Self-healing with evidence**: a healed selector is proposed (not silently saved) with before/after screenshots; owner or agent accepts → repository updated. Never guess between close candidates (keeps wad's rule).
- **Vision tier**: OmniParser V2 locally (GPU optional) for icon-only UIs; image mode for Citrix/RDP (template + OCR + anchor).
- **Wait-for-condition primitives**: element state, text appears, file exists, window idle/CPU quiet, network idle.
- **Locked-screen reality**: SendInput and screenshots fail on a locked session. Provide (a) dedicated automation VM/PC with auto-logon + screen lock disabled, or (b) "RDP-to-self keeps session alive" pattern; `control doctor` reports which is available. Tree-only (UIA pattern) actions preferred because they work on covered windows.

### 2.8 Piece 8 — Dashboard, notifications, human-in-the-loop 🟡

- **Local dashboard** (`127.0.0.1`, token): runs, step timeline with masked screenshots, errors with hints, queue items, triggers, pending approvals, "time saved" per flow, success-rate trend, flow editor (text first, visual view later).
- **Tray app**: status, pause/kill, recent runs, approve/deny.
- **Notifications**: Windows toast; optional e-mail digest; optional phone channel (only if owner approves, and never for approving risky steps unless explicitly enabled with a second factor).
- **`ask_human` step**: form (fields + validation) pops on screen or dashboard; run waits durably (hours/days) and resumes with the answer.
- **Daily/weekly report**: what ran, failures, what needs attention, disk/health from WinSight.

### 2.9 Piece 9 — Learning and discovery 🟢

- **Record → flow**: wad `record` + `trace --export` converted into a YAML flow with object-repository targets, then validated by `flow.dry_run`.
- **Describe → flow**: Claude drafts a flow from a sentence using `control.find_action` + templates; must pass `flow.validate` and a dry run before approval.
- **Task mining (local, private)**: analyse journal + optional recorder sessions for repeated sequences (PM4Py-style discovery) → "you did this 14 times this month, ~3 h — automate?".
- **Trap memory**: every failure with root cause becomes a searchable entry (the "traps learned the hard way" list, but automatic), surfaced in `control.describe` for that action.
- Flow templates library: report-to-Excel, folder-to-analysis, morning health check, invoice/PDF to records (with xl2ai verified quotes).

### 2.10 Cross-cutting: ops & quality

- Installer (`setup.ps1` → one-click), auto-update from the repo, backup/restore of config + flows + vault metadata (not secrets).
- `control doctor` extended: agent running, triggers healthy, session unlocked, broker available, disk for run store.
- Retention: run history and screenshots pruned by age/size.
- Tests: fake desktop/fake site harness for flows; chaos tests (kill agent mid-step, network drop, app hang); performance budget (engine overhead < 50 ms/step).
- KPIs shown on dashboard: runs/week, success %, mean time to recover, hours saved, approvals per week (should fall as flows mature).

### 2.11 Order of work and milestones

| Milestone | Pieces | Outcome you can see |
|---|---|---|
| M1 — "runs by itself" | 2 + 3 (time & file triggers) + agent process | first scheduled G-MES → analysis flow, survives restart |
| M2 — "safe to leave alone" | 4 + toast notifications + kill switch | unattended nightly runs with masked secrets and alerts |
| M3 — "any site, any setting" | 5 + 6 | new website or Windows setting automated without new Python |
| M4 — "doesn't break" | 7 + dashboard | UI changes heal with evidence; one page to see everything |
| M5 — "suggests work" | 9 | automation ideas from your own history |

Each piece keeps the hub process: spec → plan → build → live check on the owner's PC, with the four original repos untouched unless a piece's spec says otherwise.

### 2.12 Risks

- **Scope creep** into a generic RPA suite — every piece must ship one real owner flow before the next starts.
- **UI flows on the owner's own PC** collide with the owner's mouse — attended mode pauses on user input; unattended needs a dedicated session.
- **Corporate environment** (proxy, locked-down installs, DPAPI per user) — stdlib-first, no new services, no cloud.
- **Durable replay vs. changed flow code** — runs pin their flow version; migration only for new runs.
